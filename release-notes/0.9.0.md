# Release notes for pymetadata 0.9.0
![pymetadata](./docs/images/favicon/pymetadata-100x100-300dpi.png)

## Changes

- `pymetadata.omex` reads and writes COMBINE archives through [`pymetadata-core`](https://pypi.org/project/pymetadata-core/), which is now a dependency of pymetadata with a floor of 0.2.0. There is no pure-python fallback. The public API of `Omex`, `Manifest` and `ManifestEntry` is unchanged.
- Reading is lazy. `Omex.from_omex` no longer extracts the archive into a temporary directory, `Omex.get_path` extracts a member when something asks for it. Opening still reads the central directory and the `manifest.xml`, and inflates an unlisted `.xml` member to classify its format.
- A member which nobody touched is copied compressed when the archive is written, without being inflated and compressed again. Its compression method, compressed size and CRC are preserved exactly.
- The effect, in ms: reading with `Omex.from_omex`, writing with `Omex.to_omex` without a change. Median of 15 runs after one uncounted warm-up run. Both columns were taken with `scripts/omex_timing.py --runs 15`, the before column on a worktree of the previous release (c42df44), so the two are comparable and you can reproduce them:

  | archive | size (KiB) | entries | read before | read after | write before | write after |
  | --- | --- | --- | --- | --- | --- | --- |
  | BIOMD0000000001.omex | 277 | 16 | 2.54 | 0.24 | 11.47 | 0.23 |
  | CombineArchiveShowCase.omex | 1073 | 22 | 6.13 | 0.77 | 44.76 | 0.48 |
  | CompModels.omex | 6 | 6 | 0.69 | 0.11 | 0.48 | 0.10 |
  | iCGB21FR.omex | 1375 | 23 | 19.13 | 0.53 | 230.80 | 0.57 |

- Writing holds the archive in memory, because the core takes and returns bytes, where the previous writer streamed member by member into the temporary file. Reading reads the whole file.
- `Omex.to_directory` writes each member once, straight to its destination.

## Behaviour which changed

- A wrong or missing password raises a `ValueError` where `zipfile` raised a `RuntimeError`. The exception is a `PasswordError`, a subclass of `ValueError` in a private module, so catch `ValueError`.
- A member with an unsupported compression method, or one which inflates beyond the 1 GiB cap of the core, is refused when its bytes are read, i.e., at `Omex.get_path`, and no longer when the archive is opened. A member of this kind which the manifest does not list gets its format guessed from its suffix alone.
- A member whose name points outside of the archive, or is absolute, is refused when the archive is opened with a `ValueError`. `zipfile` sanitized such a name and read the member, this is deliberate hardening. `Omex.is_omex` still answers `True` for such a file, because it asks about the structure of the archive.
- The `manifest.xml` of a written archive is serialized by the core: there is no `master="false"` attribute and the XML declaration is single quoted. The content is the same, the bytes are not.
- A member which pymetadata writes anew, e.g., an added file or the `manifest.xml`, carries the zip epoch 1980-01-01 00:00:00 as its modification time, where the previous writer used the time of the write. A member which is copied keeps the date it had in the source archive. The upside is that a written archive is reproducible: identical content gives identical bytes. The core offers no way to set a timestamp in 0.2.0.
- A member which is copied is not inflated, so a member with a compression method the core cannot inflate, such as bzip2, survives a write unchanged (it stays bzip2), although its bytes are refused when read. Such a member makes a write at a non-default `compresslevel`, or with a `compression` other than `ZIP_DEFLATED`, fail with a `ValueError`, because those writes inflate every member.
- A location which a manifest declares twice is written once, the last entry winning, instead of producing two members of the same name.
- The entries of a written archive are in the order of the container. After a round trip the members which the manifest of the source did not list come back in the order of the container instead of sorted. Reading an archive still sorts them.
- `compression=zipfile.ZIP_STORED` is written as deflate at level 0, with a warning, because the core has no stored path. Any other `compression` than `ZIP_DEFLATED` also deflates every member again, which gives up the copy of untouched members and its speed.
- `compresslevel` keeps its meaning, and `-1` is accepted as the default level (9), as with `zipfile`. A `compresslevel` outside of 0 to 9 raises a `ValueError` as before, with a different message.
- A member which the core deflates, e.g., an added file, a member whose format or `master` flag changed, the `manifest.xml`, or any member of a write at a non-default `compresslevel`, has different bytes than before, because the deflate of the core is not the one of CPython's `zlib`. The content is identical.
- When an archive is read with `from_omex`, one warning moved to the logger `pymetadata._core_bridge` from `pymetadata.omex`: `Entry with location missing in manifest.xml`, for a member the manifest does not list (`from_directory` still logs it under `pymetadata.omex`). Two are new, both from that logger: a manifest entry which no member of the archive provides is warned about, where it used to be dropped silently (it is still dropped), and an unlisted `.xml` member whose bytes cannot be read gets its format guessed from its suffix with a warning.
- The message for a file which is not a COMBINE archive changed to `Not an OMEX archive, no readable manifest.xml: malformed ...: '<path>'.`, still a `ValueError`. Code which matches on the old text needs to be adapted.
